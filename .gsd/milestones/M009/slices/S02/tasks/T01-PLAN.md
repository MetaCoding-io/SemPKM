# T01: JWT token generation and validation

**Slice:** S02 — App SDK & IPC Proxy
**Milestone:** M009

## Description

Create the JWT token utility module for platform↔app authentication. Apps receive a token at startup (generated by AppManager), validate it on incoming requests, and can request renewal before expiry. Uses PyJWT HS256 with the platform's existing secret key. This is a pure utility with no dependencies on other S02 work — it unblocks both the proxy (T03, which injects tokens) and the SDK (T02, which validates tokens).

## Steps

1. Create `backend/app/apps/tokens.py` with two functions:
   - `generate_app_token(app_id: str, permissions: dict, secret: str, ttl_seconds: int = 3600) -> str` — encode JWT with HS256. Claims: `{"sub": f"app:{app_id}", "permissions": permissions, "iat": <now>, "exp": <now + ttl_seconds>}`. Use `datetime.now(timezone.utc)` for `iat`, `timedelta(seconds=ttl_seconds)` for `exp`. PyJWT accepts datetime objects for `exp`/`iat`.
   - `validate_app_token(token: str, secret: str, grace_seconds: int = 0) -> dict | None` — decode with `jwt.decode(token, secret, algorithms=["HS256"])`. Return decoded claims on success, `None` on any exception (`ExpiredSignatureError`, `InvalidTokenError`, etc.). For grace period: if `grace_seconds > 0`, first try normal decode; if `ExpiredSignatureError`, retry with `options={"verify_exp": False}`, check manually that `exp + grace_seconds >= now` — return claims if within grace, else None.
   - Add helper `get_secret() -> str` that calls `app.auth.tokens._get_secret_key()` — keeps the import path centralized.

2. Create `backend/tests/test_app_tokens.py` with unit tests:
   - Valid token: generate → validate returns claims with correct `sub`, `permissions`, `iat`, `exp`
   - Expired token: generate with `ttl_seconds=0`, sleep not needed — just set `exp` to past via direct `jwt.encode` or use `ttl_seconds=-1` if validator catches it. Simpler: generate with `ttl_seconds=1`, then patch `datetime.now` forward.  Best approach: generate normally, then validate with a hardcoded expired token (construct one with `exp` in the past using `jwt.encode` directly).
   - Grace period: expired token within grace → returns claims. Expired beyond grace → returns None.
   - Tampered token: modify payload after encoding → returns None
   - Wrong secret: validate with different secret → returns None
   - Missing claims: token without `sub` → still returns decoded dict (no claim enforcement in validator — enforcement is SDK-side)
   - Wrong algorithm: encode with HS384, decode expects HS256 → returns None
   - Claims structure: verify `sub` format is `"app:{app_id}"`, `permissions` dict present
   - get_secret() returns a string

## Observability Impact

- `generate_app_token()` logs at DEBUG with app_id and expiry timestamp on every token generation
- `validate_app_token()` logs at DEBUG on successful validation (with sub claim), WARNING on invalid tokens (with exception type, no token value leaked)
- `_validate_with_grace()` logs at DEBUG whether an expired token was accepted or rejected within the grace window
- Future agents can inspect token behavior via: `grep "app token" <logfile>` — covers generation, validation success, and rejection reasons
- No persistent failure state — this is a stateless utility; failures surface as None return values logged at the call site
