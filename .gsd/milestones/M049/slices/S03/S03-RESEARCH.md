## Implementation Landscape

### 1. Server-Timing Per-Query Breakdown

**Current state:** `TimingMiddleware` in `backend/app/middleware/timing.py` adds `Server-Timing: total;dur=X` to every response. No per-query breakdown.

**Target:** `Server-Timing: total;dur=1234.56, sparql.1;dur=345.67, sparql.2;dur=456.78`

**Approach: `contextvars.ContextVar` for request-scoped timing accumulation.**

The middleware sets a `ContextVar[list[tuple[str, float]]]` at request start. The TriplestoreClient's span-instrumented methods (`query()`, `update()`, `construct()`, `insert_graph()`) append `(span_name, duration_ms)` entries. The middleware reads the list after `call_next()` and serializes into the `Server-Timing` header.

**Files to modify:**
- `backend/app/middleware/timing.py` — add `ContextVar`, populate in middleware, serialize into header
- `backend/app/triplestore/client.py` — add `time.monotonic()` timing + append to ContextVar in each span method

**Why ContextVar over OTel span reading:** The OTel SDK's `BatchSpanProcessor` exports spans asynchronously. Span data isn't synchronously available in the middleware after `call_next()`. A simple ContextVar with `time.monotonic()` deltas is reliable and zero-overhead.

**Key detail:** The ContextVar must be imported in both files. The token returned by `.set()` should be used to reset the var after the request (prevents leaking between requests in the same asyncio task).

### 2. Admin Performance Dashboard

**Current state:** 
- JSON API at `GET /api/admin/timing-report` (owner-only, returns `top_endpoints` list with p95, avg, max, min, count)
- No HTML admin page for performance visualization
- Admin page pattern: `backend/app/admin/router.py` serves Jinja2 templates from `backend/app/templates/admin/`, prefixed `/admin`, gated by `require_role("owner")`
- Chart.js reference pattern: `model_detail.html` uses `{{ 'chartjs.js' | asset_url }}` in a `{% block scripts %}` tag

**Target:** `/admin/performance` page with:
- Top 10 slowest endpoints bar chart (avg_ms)
- Percentile breakdown (p50/p95/p99) per endpoint
- Request count and collection period info
- Auto-refresh option

**Approach:**
1. Add a new route `GET /admin/performance` to `backend/app/middleware/timing.py` (alongside the existing JSON endpoint in `timing_router`) — or better, keep it in the admin router for consistency
2. Extend `get_timing_report()` to include p50 and p99 in addition to the existing p95
3. Create `backend/app/templates/admin/performance.html` extending `base.html`
4. Use Chart.js bar chart with grouped bars for p50/p95/p99
5. Add a card to `backend/app/templates/admin/index.html` linking to `/admin/performance`

**Decision point: Which router?** The timing JSON endpoint is on `timing_router` (prefix `/api/admin`). The HTML admin pages are on `admin_router` (prefix `/admin`). The HTML performance page should be on the `admin_router` for consistency with all other admin pages. The JSON data can come from the existing `/api/admin/timing-report` endpoint (fetched client-side via JS) or passed as template context. Template context is simpler — no extra fetch.

**Chart.js availability:** `chartjs.js` is referenced via `asset_url` filter. In dev mode this resolves to `/js/chartjs.js`. The file is generated by a build pipeline (`frontend/build/` or equivalent). The `model_detail.html` already uses this pattern successfully. If the file is missing in dev, Chart.js can be loaded from CDN as a fallback (matching the calendar/map view pattern from KNOWLEDGE.md). Safer approach: use CDN with local fallback, or just use CDN since this is an admin page.

### 3. Lazy-Load Right Pane Panels (R001)

**Current state:**
- `backend/app/templates/browser/partials/inbox_panel.html`: `hx-trigger="load, every 60s"` on the inbox content div
- `backend/app/templates/browser/partials/collaboration_panel.html`: `hx-trigger="load"` on the collab content div
- Both are `<details>` elements — `hx-trigger="revealed"` fires when the element enters the viewport (htmx built-in)

**Target:** Change to `hx-trigger="revealed"` so requests fire only when the `<details>` is expanded and the content div scrolls into view.

**Important nuance:** The inbox panel uses `hx-trigger="load, every 60s"`. Changing to `revealed` means the 60s polling also needs adjustment. Options:
- `hx-trigger="revealed, every 60s"` — polls once revealed, which is correct (only polls when visible)
- `hx-trigger="revealed"` — loads once on reveal, no polling. Simpler but loses auto-refresh.
- Best: `hx-trigger="revealed, every 60s [intersecting]"` — but htmx doesn't support conditional polling natively.

The simplest correct approach: `hx-trigger="revealed once, every 60s"` won't work because `once` prevents the 60s from firing. Better: just change `load` to `revealed` and keep `every 60s` — htmx `revealed` fires when the element enters the viewport, and `every 60s` continues independently. The key requirement (R001) is that the *initial* load doesn't fire on page load — and `revealed` achieves that. The 60s polling is acceptable after reveal since it keeps the inbox fresh.

**Files to modify:**
- `backend/app/templates/browser/partials/inbox_panel.html` — change `hx-trigger="load, every 60s"` to `hx-trigger="revealed, every 60s"`
- `backend/app/templates/browser/partials/collaboration_panel.html` — change `hx-trigger="load"` to `hx-trigger="revealed"`

**Both panels are `<details>` elements.** The collaboration panel is not `open` by default; inbox is `open`. For the inbox (`open` by default), `revealed` fires when the element enters the viewport — which means it will fire on initial workspace load *if the right pane is visible and the inbox details is expanded and scrolled into view*. If the right pane is closed or the inbox is below the fold, it won't fire. This satisfies R001 — the request is conditional on visibility, not unconditional on page load.

## Constraints & Pitfalls

1. **ContextVar cleanup:** Must use the reset token from `.set()` to prevent leaking timing data between requests on the same asyncio task. Pattern: `token = _sparql_timings.set([]); ... ; _sparql_timings.reset(token)`.

2. **Server-Timing name uniqueness:** Multiple SPARQL queries in one request need unique names. Use incrementing index: `sparql.1;dur=X, sparql.2;dur=Y`. The names don't need to be semantically meaningful — DevTools shows them in order.

3. **Chart.js in admin template:** The `{{ 'chartjs.js' | asset_url }}` pattern works if the asset is present. Since `model_detail.html` already uses this exact pattern, follow it. If the file doesn't exist in dev mode, the chart won't render — acceptable for a dev-only admin page.

4. **htmx `revealed` vs `load`:** `revealed` is an htmx extension-free built-in trigger that fires when the element enters the viewport via IntersectionObserver. It's the correct primitive for lazy-loading. No htmx extensions needed.

5. **Inbox polling after reveal:** Keep `every 60s` alongside `revealed` for the inbox to maintain auto-refresh behavior. The `revealed` replaces only the `load` trigger.
