# Memory palace mode: engines, map formats, editors, art assets, rendering, accessibility, persistence and multiplayer

Research date: 3 November 2026. Scope: practical technology for a 2D top-down tile-based walkable world with an in-app level editor, delivered as an installable SemPKM app (subprocess + SDK, custom pages) on an htmx + vanilla-JS (esbuild) frontend with a FastAPI/RDF backend. Where a release page omitted the year, that is noted; several "2026" datings below are inferred from neighbouring releases and flagged as such.

## Key question 1: Which engine (Phaser 3/4, PixiJS v8, Excalibur, Kaplay, melonJS, Godot 4 web, plain Canvas 2D, SVG/DOM) suits a no-framework esbuild project with modest scope?

### Takeaway
For one map at a time, a few sprites and collision-only "physics", the two best fits for a vanilla-JS/esbuild app are (a) a thin home-grown Canvas 2D renderer (zero dependencies, full control over integer scaling and DOM overlays) or (b) melonJS 20 (MIT, ~250 KB minzipped, no dependencies, tree-shakeable ESM, Tiled 1.12 support built in, very actively released through October 2026). Phaser 4 is the most mature full engine but ships 1.27 to 1.38 MB minified; PixiJS is a renderer rather than a game engine (no built-in Tiled parser, camera or input abstraction); Kaplay's v4000 is still alpha; Godot web exports are tens of MB and require cross-origin-isolation headers that would affect the whole host origin.

### Inferences
- Maintenance status, 2026: Phaser 4 is the active line (three minor releases April to July 2026); Phaser 3 has had no release since v3.90.0 (May 2025), so it is effectively frozen. melonJS is the most frequently released small engine (roughly weekly 20.x releases through Oct 2026) with the lowest open-issue count. Excalibur releases roughly quarterly. Kaplay's stable line is 3001.x; v4000 has been in alpha for over a year.
- Bundle budget: melonJS (~250 KB minzipped) is roughly 2 to 3x the gzipped size of PixiJS core (~244 KB gz is PixiJS *without* a tilemap plugin or any game loop/camera/input helpers), and a fraction of Phaser's 1.27 to 1.38 MB minified (gzipped size not found; see gaps). A hand-rolled Canvas 2D renderer for a 36x20 to 100x100 orthogonal map with a handful of sprites would plausibly be 10 to 30 KB of application code and zero dependencies, which matches SemPKM's existing "spatial canvas" approach.
- Fit for a no-framework esbuild app: all JS engines above are framework-agnostic ESM packages and bundle fine with esbuild. Phaser 4 and melonJS both consume Tiled JSON natively; Excalibur needs its plugin; PixiJS would need custom Tiled parsing plus `@pixi/tilemap`.
- Godot is a poor fit for an embedded "mode" inside a PKM web app: 5 MB+ download before assets, and COOP/COEP headers (if threads are enabled) apply to the whole SemPKM origin and would break embedding third-party iframes elsewhere in the app. A single-threaded export avoids the headers but the size remains.
- SVG/DOM tiles are workable for the small end (36x20 = 720 tiles) and give free accessibility hooks (real elements for ARIA), but at 100x100 = 10,000 tiles, with pan/zoom, the evidence above suggests DOM will stutter; a canvas world with a DOM overlay for labels/UI is the safer middle path.

## Key question 2: Map format and editor — Tiled TMJ/TMX, how WorkAdventure attaches behaviour via Tiled properties, LDtk, and whether to build an in-app editor (and existing open-source web editors)

### Takeaway
Tiled's JSON (TMJ) is the de facto interchange format: tile layers, object layers, typed custom properties (including `class` and `object` references), templates, Wang/terrain sets and per-tile collision shapes are all first-class, and WorkAdventure demonstrates a complete "behaviour via properties" convention (`floorLayer`, `collides`, `start`/`startLayer`, `exitUrl`). LDtk is MIT but desktop-only. No mature, permissively licensed, vanilla-JS, in-browser tile editor with autotiling exists; the closest are small hobby projects, so an in-app editor would be built in-house while reading/writing TMJ-compatible JSON.

### Cited Findings

**Tiled JSON (TMJ) format**
- Map: `type:"map"`, `version` (string since 1.6), `tiledversion`, `class` (1.9), `width`/`height` in tiles, `tilewidth`/`tileheight`, `infinite`, `orientation` (orthogonal, isometric, staggered, hexagonal), `renderorder`, `layers`, `tilesets`, `properties`, `nextlayerid`, `nextobjectid`. — [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)
- Layer types: `tilelayer` (`data` as GID array or base64; `encoding` csv/base64; `compression` zlib/gzip/zstd; `chunks` for infinite maps), `objectgroup` (`objects`, `draworder` topdown/index), `imagelayer`, `group` (nested `layers`). Layers carry `id`, `name`, `visible`, `opacity`, `offsetx/y`, `parallaxx/y`, `tintcolor`, `mode` (blend, 1.12), `class`, `properties`. — [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)
- Objects: `id`, `name`, `type` (renamed `class` in 1.9, restored to `type` in 1.10), `x`, `y`, `width`, `height`, `rotation`, `visible`, `properties`; kinds: `gid` (tile object), `ellipse`, `point`, `polygon`, `polyline`, `capsule` (1.12), `template` reference, `text` (with `fontfamily`, `pixelsize` default 16, `wrap`, `color`, etc.). — [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)
- Custom properties: each has `name`, `type`, `value`, optional `propertytype`; types `string`, `int`, `float`, `bool`, `color`, `file`, `object` (1.4), `class` (1.8, value is an arbitrary JSON object). Custom property types (1.8) are referenced via `propertytype`. — [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)
- Wang sets (terrain/autotiling): `name`, `type` (`corner`, `edge`, `mixed`; 1.5), `colors` (each with `name`, `color`, `probability`, `tile`), `wangtiles` (`tileid` + `wangid`, an array of 8 colour indexes). Wang sets replaced per-tile `terrain` arrays in 1.5. — [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)
- Templates: separate JSON files with `type:"template"` containing an optional external `tileset` and an `object`; instances reference them via the object's `template` field. — [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)
- Tilesets: `firstgid`, `image`, `columns`, `tilecount`, `tilewidth/height`, `margin`, `spacing`, `tiles[]` with `id`, `animation` (frames `tileid`+`duration`), `objectgroup` (collision shapes), `probability`, `properties`, `type`; `wangsets`; `transformations` (hflip/vflip/rotate). Local ID = GID minus `firstgid`. — [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)

**WorkAdventure's conventions on top of Tiled**
- Map MUST be orthogonal, tiles 32x32, exported as JSON (Tiled 1.3+), tilesets MUST be embedded (no external TSX). Map MUST contain an `objectgroup` layer named `floorLayer`; every layer above it is drawn on top of characters. — [WorkAdventure: About WA maps](https://docs.workadventu.re/map-building/tiled-editor/wa-maps)
- `collides` (bool) is set on individual tileset tiles only (not layers or objects). Other properties may be placed on tiles, Tiled objects or whole layers; a property on an object fires when the avatar enters that object's area, a property on a layer fires when the avatar walks on any tile of that layer. — [WorkAdventure: About WA maps](https://docs.workadventu.re/map-building/tiled-editor/wa-maps)
- Map-level metadata properties: `mapName`, `mapLink`, `mapDescription`, `mapCopyright`, `mapImage`; `tilesetCopyright` (tileset); `audioCopyright` (layer). — [WorkAdventure: About WA maps](https://docs.workadventu.re/map-building/tiled-editor/wa-maps)
- Entries/exits: a layer named `start` (tiles in it are spawn points; multiple tiles = random spawn); `startLayer` (bool, true) marks another layer as a named entry; tile property `start` (string) names an entry point; `exitUrl` (string, layer) sends the player to another map when they step on any tile of that layer, one layer per exit; `exitSceneUrl` and `exitInstance` are deprecated. Entry points are selected via URL hash (`#entryPointName`), `moveTo=` accepts a layer name, object name or x,y. — [WorkAdventure: Entry/exit](https://docs.workadventu.re/map-building/tiled-editor/entry-exit)
- WorkAdventure ships a Map Starter Kit (default office tileset, local web server, upload to WA or GitHub Pages, TypeScript scripting API); sample map `office.tmj`; "simple changes like furniture and entries/exits" are done in WorkAdventure's own inline editor rather than Tiled. — [WorkAdventure: Tiled editor](https://docs.workadventu.re/map-building/tiled-editor/)

**LDtk**
- LDtk's JSON page is for version 1.5.3; project data is plain JSON; JSON_SCHEMA.json, MINIMAL_JSON_SCHEMA.json and QuickType files are provided. — [LDtk JSON docs](https://ldtk.io/json/)
- LDtk is MIT-licensed; runs through Electron (`npm run start`) or NW.js; no web/browser build mentioned; 7,375 commits. — [deepnight/ldtk](https://github.com/deepnight/ldtk)

**In-browser / open-source tile editors**

- blurymind/tilemap-editor: "fat-free tile map editor with zero dependencies", vanilla JS, no build step; unlimited layers with opacity/visibility, bucket fill, random tile tool, undo/redo; no autotile listed. — [blurymind/tilemap-editor](https://github.com/blurymind/tilemap-editor)
- SanjoSolutions/tilemap-editor: TypeScript browser app with layers and undo. — [SanjoSolutions/tilemap-editor](https://github.com/SanjoSolutions/tilemap-editor); radiantBear/Tile-Editor lists undo/redo and bucket fill only as planned. — [radiantBear/Tile-Editor](https://github.com/radiantBear/Tile-Editor); Tactile is a desktop (not browser) editor with extensive undo/redo. — [albin-johansson/tactile](https://www.Github.com/albin-johansson/tactile)
- Sprite Fusion is proprietary: "Freemium (Pay once)", one-time purchase of $12 plus a limited free version; Defold lists its licence as "N/A". Open-source importers for its export exist (Flame package MIT; Bevy plugin). — [AlternativeTo: Sprite Fusion](https://alternativeto.net/software/sprite-fusion/about); [Defold asset page](https://defold.com/assets/spritefusion); [flame_sprite_fusion licence](https://pub.dev/packages/flame_sprite_fusion/license)
- Kaplay: no level editor; KAPLAYGROUND is a code playground. — [kaplayjs/kaplay](https://github.com/kaplayjs/kaplay)

### Inferences
- A SemPKM palace file can be a strict subset of TMJ: orthogonal map, 2 to 4 `tilelayer`s (floor, walls/furniture, overlay-above-avatar), one `objectgroup` for "placements" (each object a `point` or tile object whose `properties` hold `sempkm:iri`, `sempkm:type`, label), plus `class`-typed properties for room metadata. Staying TMJ-compatible means power users can round-trip through desktop Tiled, and both melonJS and Phaser can load the file unchanged.
- WorkAdventure's model (behaviour as typed properties on tiles/layers/objects, `collides` on tileset tiles, a named floor layer separating under/over-avatar drawing) is a proven pattern to copy for the "interact to open object" behaviour.
- In-app editor scope that is realistic to build in vanilla JS: grid painting with a tile palette, rectangle and flood fill, eraser, layer switching, undo/redo via an array of inverse patches, and Wang-set (blob/47-tile or 16-tile corner) autotiling driven by the tileset's `wangsets` definition. None of the surveyed browser editors is suitable as a drop-in component (React/Rust stack, unverified licences, hobby maintenance), but blurymind/tilemap-editor is useful as a reference implementation for a dependency-free UI.
- LDtk's IntGrid + auto-layer rules are the best reference for *rule-based* autotiling, but the editor cannot be embedded in a browser; its JSON could be an alternative import format but offers no advantage over TMJ here.

## Key question 3: Art assets — CC0/permissive top-down tilesets and characters for an office/library/study palace, resolution and style, consistent furniture set, type colouring, character generators

### Takeaway
For a permissive, attribution-free base, Kenney's packs (CC0, 16x16: Roguelike/RPG Pack 2015, Tiny Town 2023) and Pixel Boy's Ninja Adventure (CC0, 16x16, updated March 2026, 50+ characters, interior elements) are the safest; 0x72's Dungeon Tileset II is CC0 but dungeon-themed. LPC is rich in indoor furniture but is CC-BY-SA 3.0 / GPL 3.0 with per-file credits, and the Universal LPC generator code is GPL-3.0. Limezu's Modern Interiors is the best-matching office/library furniture set (16/32/48 px, libraries, classrooms) but is paid, requires credit and forbids redistribution, which matters for an installable app that ships its assets.

### Cited Findings
- Kenney Roguelike/RPG Pack: licence CC0 1.0; 16x16 tiles; version 1.0 released 2015; tags include "furniture", "town", "roguelike", "rpg"; ~1700 files listed. — [Kenney Roguelike/RPG Pack](https://kenney.nl/assets/roguelike-rpg-pack)

### Inferences
- Resolution: 16x16 is the common denominator across the CC0 sets (Kenney, Ninja Adventure, 0x72) and Limezu offers 16/32/48. Rendering 16px art at 3x or 4x integer zoom (48 or 64 CSS px per tile) gives a 36x20 map of 1,728 to 2,304 px width, which suits a tab in a desktop PKM app; 32px art at 2x gives the same footprint with more detail but fewer free sources.
- Consistent furniture set (desk, bookshelf, lectern, board, plant, sofa, signpost): Limezu is the only surveyed set that clearly covers all of these in office/library themes, but its no-redistribution clause means the installable app could not bundle the PNGs; it could only instruct users to drop their own purchased copy into a folder. A CC0 route would combine Kenney Roguelike/RPG (tagged furniture) with Ninja Adventure interiors and commission or draw the missing items (lectern, whiteboard, signpost) in the same palette.
- Type-coloured recolouring: with CC0 art, palette-swapping sprites at load time (canvas `getImageData` hue/tint, or pre-generated tinted copies per object type) is permissible; with LPC (CC-BY-SA) derived tints must remain share-alike, and with Limezu derived files may not be redistributed. A simpler, licence-neutral approach is to leave sprites untouched and draw a type-coloured outline, base plate or badge under/over the sprite.
- Character generator: the Universal LPC generator is the only free, browser-based generator found; its exported credits CSV should be stored alongside each generated sheet. Its GPL-3.0 code licence only matters if the generator itself is embedded; using its PNG output is governed by the art licences (mostly CC-BY-SA 3.0).

### Gaps
- No source gave exact tile counts for the Kenney packs (only file counts), nor an itemised furniture list for any pack.
- Limezu's licence text was read from the itch page summary; the full licence file inside the download was not reviewed.
- No specific CC0 set with lectern, whiteboard and signpost sprites in one consistent style was identified; this may require custom pixel art.
- OpenGameArt and itch.io were not searched broadly for additional office/library CC0 sets beyond those named in the brief.

## Key question 4: Rendering text and labels crisply with pixel art, pixel-perfect scaling, and Canvas vs DOM performance for 36x20 to 100x100 maps

### Takeaway
Crisp pixel art needs integer scale factors, `imageSmoothingEnabled = false` re-applied after any resize, whole-pixel sprite coordinates and CSS `image-rendering: pixelated` (which distorts at non-integer scales). No rigorous DOM-vs-canvas tile benchmark was found, but the available evidence consistently favours canvas once element counts reach ~1,000, so a 100x100 map (10,000 tiles) should be canvas with viewport culling, while labels and UI text should live in a DOM overlay so they stay vector-sharp at any zoom.

### Cited Findings
- MDN describes giving canvas/WebGL games "a crisp pixel art look, even on high definition monitors" using CSS `image-rendering`; scaling by non-integer factors (e.g. 128 px drawn into 100 px, 0.78 px per image pixel) "can lead to blurriness"; the fix is to keep image pixels at integer multiples of canvas pixels. — [MDN: Crisp pixel art look with image-rendering](https://developer.mozilla.org/en-US/docs/Games/Techniques/Crisp_pixel_art_look)
- CSS `image-rendering: pixelated` is "useful when zooming pixel art to integer multiples (300%, 400%, etc.)" and distorts at non-integer scales; a proposed (untested) workaround is to scale to the nearest integer first, then scale down. — [W3C public-css-archive, Jan 2021](https://lists.w3.org/Archives/Public/public-css-archive/2021Jan/0055.html)
- Practical 2D canvas recipe: set `ctx.imageSmoothingEnabled = false` after every resize or context change, compute an integer scale from the window size, draw sprites at whole-pixel coordinates (sub-pixel positions blur), and cull to the visible tile range from camera position and canvas size. — [Cinevva: Pixel art rendering tutorial](https://app.cinevva.com/tutorials/pixel-art-rendering)
- "The overhead of DOM rendering is more poignant when juggling hundreds if not thousands of objects; in this scenario, canvas is the clear winner." — [LogRocket](https://blog.logrocket.com/when-to-use-html5s-canvas-ce992b100ee8)
- DOM-based infinite canvases "start lagging around 1,000 elements during zoom operations", worst during zoom, compounded by text and shadow rendering; PixiJS gave ~10x gains (anecdotal). — [thebiggish.pages.dev report](https://thebiggish.pages.dev/news/developer-pushes-pixi-js-infinite-canvas-to-60-000-cards-before-performance-breaks)
- A 2013 mobile benchmark (Collie) found mixed results, with DOM sometimes beating canvas on old Android and canvas winning on iOS; dated. — [Collie benchmark wiki](https://github.com/davidshimjs/collie-benchmark/wiki/Performance-Benchmark)
- A May 2026 ITNext article compares DOM, SVG, Canvas and GPU rendering in headless Chromium with 10 runs and medians; numbers not retrieved. — [ITNext: Four ways the browser renders graphics](https://itnext.io/four-ways-the-browser-renders-graphics-four-costs-206c4eec7452)

### Inferences
- Draw the world to an offscreen canvas at native 16 px tile resolution and blit it to the visible canvas at an integer zoom (2x, 3x, 4x) chosen from the container size; snap camera and avatar positions to integer native pixels. Expose zoom steps only as integers.
- Text: canvas-drawn text at 3x/4x integer zoom with smoothing disabled looks jagged; drawing labels in an absolutely positioned HTML layer over the canvas (positioned from world-to-screen transforms) keeps labels crisp, lets them scale with browser zoom, and gives screen readers real text. Alternatively use a pixel bitmap font (Ninja Adventure ships two fonts under CC0) for in-world signage.
- Performance budget: 36x20 = 720 tiles per layer; 100x100 = 10,000 tiles per layer. With 3 layers and viewport culling (e.g. a 1,280x720 viewport at 3x shows ~27x15 = 405 tiles per layer), per-frame draw calls stay in the low thousands of `drawImage` calls at most, well within Canvas 2D budget. Pre-rendering static layers to an offscreen canvas and redrawing only the avatar/dynamic layer reduces this further. DOM tiles at 10,000 nodes would be at the "starts lagging" threshold the sources describe, especially during pan/zoom.

### Gaps
- No peer-reviewed or reproducible benchmark of DOM vs canvas specifically for tile maps was found; the ITNext 2026 article may contain figures but was not fetched.
- No source on text rendering quality on canvas versus DOM at integer pixel-art zooms; this is an inference.

## Key question 5: Accessibility — keyboard navigation, screen-reader alternatives, motion sensitivity, colour-blind-safe type colouring, and applicable guidelines

### Takeaway
The Game Accessibility Guidelines (GAG) and Xbox Accessibility Guidelines v3.2 (June 2023) provide the applicable checklists: remappable controls, same input for UI and gameplay, no essential information by colour alone, high contrast and adjustable text, avoid flicker, option to disable background movement, screen reader (narration) support. For a canvas world the practical pattern is a parallel DOM "room list / object list" mode plus an ARIA live region announcing room and nearby objects; this was not found as a documented guideline for 2D games specifically and is an inference from the general guidance.

### Cited Findings
- GAG items relevant here (level in brackets): "Allow controls to be remapped / reconfigured" (Basic); "Ensure that all areas of the user interface can be accessed using the same input method as the gameplay" (Basic); digital controls should handle all key actions with other input methods as extras (Intermediate); "Ensure screen reader support, including menus & installers" (Advanced); "Ensure screenreader support for mobile devices" (Intermediate); "Ensure manual / website are provided in a screenreader friendly format" (Intermediate); "Use an easily readable default font size" (Basic); "Provide high contrast between text/UI and background" (Basic); "Provide an option to adjust contrast" (Intermediate); "Allow the font size to be adjusted" (Advanced); "Ensure no essential information is conveyed by a fixed colour alone" (Basic); "Include an option to adjust the sensitivity of controls" (Basic); "Avoid (or provide option to disable) any difference between controller movement and camera movement" (Intermediate); "Provide an option to turn off / hide background movement" (Intermediate); "Avoid any sudden unexpected movement or events" (Advanced); "Avoid flickering images and repetitive patterns" (Basic); "Ensure no essential information is conveyed by sounds alone" (Basic). — [Game Accessibility Guidelines: full list](https://gameaccessibilityguidelines.com/full-list/)
- Xbox Accessibility Guidelines: current version 3.2 published 8 June 2023; described by Microsoft as best practices built with industry experts and the gaming disability community, "not a compliance checklist"; XAG 106 covers Screen narration; XAG 103 covers additional channels for visual and audio cues; XAG 105 (Audio accessibility) includes automatically lowering or muting game audio when a screen reader is detected; a version-history note adds that tables should be fully accessible to screen narration. — [XAG overview](https://learn.microsoft.com/gaming/accessibility/guidelines); [XAG 103](https://learn.microsoft.com/en-gb/gaming/accessibility/xbox-accessibility-guidelines/103); [XAG 105](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/105); [XAG version history](https://learn.microsoft.com/ar-sa/xbox/accessibility/xag-version-history)
- melonJS cameras support shake, fade and flash effects (features that GAG says should be avoidable/disableable). — [melonjs/melonJS](https://github.com/melonjs/melonJS)

### Inferences
- Keyboard: arrow/WASD movement plus a single "interact" key (Enter/Space) and Escape to leave the world satisfies the "same input method for UI and gameplay" rule if the editor palette and dialogs are also keyboard-operable; expose remapping in settings.
- Screen-reader alternative: because canvas content is invisible to assistive tech, provide (a) a DOM "room list" mode listing rooms and the objects placed in each as real links/buttons (this reuses SemPKM's existing object tabs), and (b) an `aria-live="polite"` region updated on room entry ("Entered Library, 4 objects nearby: Thesis notes, ...") and on facing an object. Both are cheap in htmx/vanilla JS and align with GAG "screen reader support" and XAG 106.
- Motion: offer "reduced motion" (respect `prefers-reduced-motion`): instant camera snaps instead of smooth follow, no screen shake, no idle animations; offer teleport-to-room from the room list so walking is optional.
- Colour-blind-safe type colouring: never rely on colour alone (GAG Basic); pair each object type with a distinct sprite/icon or badge shape and a text label; use a colour-blind-safe categorical palette (SemPKM's existing dataviz palette rules apply).

### Gaps
- No W3C/WAI work specific to games accessibility was found in this pass (the search returned only GAG and XAG); WCAG applies to the surrounding web UI but has no canvas-game-specific guidance that I could cite.
- XAG 106 (Screen narration) content itself was not fetched; only its existence and version.
- No published example of an ARIA live-region pattern for a 2D tile world was found; the design above is an inference.

## Key question 6: Persistence — tile map, rooms and placements as RDF vs JSON blob, size estimates, and how WorkAdventure/Gather store maps

### Takeaway
WorkAdventure stores maps as TMJ files served by a dedicated map-storage service (filesystem with an S3-compatible option visible in its compose files), not as rows in a database. For SemPKM, a hybrid is the natural fit: tile layers as a TMJ-compatible JSON blob (tens of KB even at 100x100) written through the command API, while rooms and placements (object IRI, room, position, type) are RDF so they can be queried, linked and visited from the graph.

### Cited Findings
- WorkAdventure maps are `.tmj` files; maps are uploaded to a WorkAdventure server or hosted on GitHub Pages. — [WorkAdventure: Tiled editor](https://docs.workadventu.re/map-building/tiled-editor/)
- WorkAdventure's deployment has a separate `map-storage` service (alongside `play`, `back`, `uploader`, `icon`) behind an nginx/Traefik gateway at a `/map-storage` route, through which users upload their own maps. — [Zeabur WorkAdventure template](https://zeabur.com/templates/D42TJ1.yaml)
- The main repo lists `play`, `front`, `back`, `map-storage`, `uploader`, `maps`, `api`, `icon`, Matrix/Synapse (chat), OIDC mock, Traefik, LiveKit; a `docker-compose.rustfs.yaml` suggests an S3-compatible storage option; Redis appears as a hostname. — [workadventure/workadventure](https://github.com/workadventure/workadventure)
- Tiled tile layer `data` is an array of GIDs (CSV) or base64 (optionally zlib/gzip/zstd compressed); object layers carry typed `properties` including `object` references and `class` structs. — [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)

### Inferences
- Size estimates (arithmetic): a 36x20 map has 720 cells per layer; at 3 tile layers that is 2,160 GIDs, roughly 6 to 10 KB as CSV JSON or ~2.9 KB as base64 of uint32. A 100x100 map has 10,000 cells per layer; 3 layers = 30,000 GIDs, roughly 90 to 150 KB as CSV JSON (3 to 5 bytes per GID) or ~40 KB as base64 uint32 (53 KB base64), and far less with zlib since palace maps are highly repetitive. Either is trivial to store as a single JSON literal/blob and to diff for undo history.
- RDF for tiles is a poor fit: 30,000 cells would mean at least 30,000 triples (more with layer/position reification) for data that has no semantic meaning beyond rendering, and every paint stroke would be a bulk write. Storing the TMJ blob as one literal (or a file referenced by IRI) in the triplestore, versioned by the command API, keeps the audit trail without exploding the graph.
- RDF for rooms and placements is a good fit: `palace:Room` (label, bounds in tiles, colour/type), `palace:Placement` linking a SemPKM object IRI to a room and a tile coordinate, plus `palace:door` relations between rooms. This mirrors the TMJ object layer one-to-one (each Tiled object with `sempkm:iri`), so the blob and the graph can be kept in sync by the app's command handlers, and queries like "which objects are in the Library" or "where is object X" are plain SPARQL.
- WorkAdventure's example shows that a flat-file TMJ plus a thin storage service is sufficient at scale; SemPKM's app-as-subprocess can own a `maps/` directory or write the blob through the SDK.

### Gaps
- No documentation on how Gather.town stores maps was found (not searched in depth; Gather's internals are proprietary).
- WorkAdventure's exact map-storage backend (filesystem vs S3 default) and its Redis usage were not confirmed from docs; only compose/template file names were seen.

## Key question 7: Multiplayer later — minimal options for syncing avatar positions in a self-hosted Python backend (FastAPI WebSockets, Colyseus, polling) and what WorkAdventure uses

### Takeaway
FastAPI/Starlette WebSockets with an in-memory connection manager are enough for a single-process self-hosted palace (with `encode/broadcaster` over Redis if multiple workers are ever needed). Colyseus (MIT, 0.17 line in 2026) is the mature Node alternative but adds a second runtime. WorkAdventure uses a Node "pusher" (WebSocket/HTTP front door, historically on uWebSockets.js, later wrapped with HyperExpress) forwarding to a "back" service over gRPC, under an AGPLv3 + Commons Clause licence that is not OSI-approved.

### Cited Findings
- FastAPI WebSockets: install `websockets`; define `@app.websocket("/ws")` endpoints with `await websocket.accept()`, `receive_text()/send_text()` (also binary and JSON); `WebSocketDisconnect` on client disconnect; `Depends`, `Cookie`, `Header`, `Query` work in WebSocket endpoints; raise `WebSocketException` with RFC 6455 close codes for auth failures; the documented `ConnectionManager` keeps `active_connections: list[WebSocket]` and loops to `broadcast()`; the docs warn this "only works while a single process is running" and recommend encode/broadcaster (Redis, PostgreSQL, etc.) for multi-process setups. — [FastAPI: WebSockets](https://fastapi.tiangolo.com/advanced/websockets/)
- Colyseus is MIT-licensed; main repo last pushed 2026-04-08 with a CHANGELOG_0.17.md; `@colyseus/shared-types` 0.17.6 updated 5 Feb 2026; scaffold via `npm create colyseus-app@latest`. — [colyseus/colyseus](https://www.github.com/colyseus/colyseus); [ecosyste.ms snapshot](https://awesome.ecosyste.ms/projects/github.com%2Fcolyseus%2Fcolyseus); [socket.dev @colyseus/shared-types](https://socket.dev/npm/package/@colyseus/shared-types)
- WorkAdventure architecture: a Pusher container was added in 2020 as "middleware/dispatcher between front and back". — [Binary Kitchen mirror commit](https://git.binary-kitchen.de/noby/workadventure/src/commit/e5138e1c034d8abbea0e592af65bb5f992b0cb2e). The pusher accepts WebSocket and HTTP connections from the front and forwards them to the correct "api" (back) server; an older guide pins `uWebSockets.js` to `uNetworking/uWebSockets.js#v19.3.0`; the back runs HTTP on 8080 and gRPC on 50051; a later commit wraps the WebSocket layer with HyperExpress. — [Running WorkAdventure without Docker](https://www.champonthis.de/dev/rand/workadventure); [partey_workadventure pusher commit](https://git.bstly.de/_Bastler/partey_workadventure/src/commit/6540f15c5bfbd182c97d10ed93450abd468a3e69/pusher)
- WorkAdventure self-hosted licence: "AGPL v3 license modified by the Commons Clause"; you cannot run it as an online subscription service; "not considered OSI compliant". — [WorkAdventure FAQ: licence](https://workadventu.re/faq/what-is-the-license-of-the-self-hosted-version-of-workadventure/); [Pricing & licensing](https://workadventu.re/support/pricing-and-licensing/)

### Inferences
- Minimal viable sync for "others may visit": one WebSocket per visitor to the palace app's FastAPI subprocess; clients send `{x, y, facing}` at ~10 Hz (tile-granular moves can be event-driven instead of fixed-rate), the server broadcasts a per-room snapshot to the other connections in that palace; client-side interpolation between snapshots. At the expected scale (a handful of visitors), the single-process in-memory manager in the FastAPI docs is sufficient; add `broadcaster` + Redis only if the app runs under multiple workers.
- Polling (HTTP every 500 to 1000 ms) works through htmx without any WebSocket code, but gives visibly jerky avatars; it is acceptable as a fallback behind restrictive proxies.
- Colyseus would be justified only if the project wanted schema-synced room state, reconnection and matchmaking out of the box; it requires a Node process alongside the Python app, so it is a poor fit for an app platform whose SDK is Python-centric.
- WorkAdventure's code cannot be reused as a component because of the Commons Clause (and because it is Phaser/TypeScript/Node), but its protocol shape (WebSocket front door, room-scoped broadcast, gRPC between pusher and back) is a reasonable reference.

### Gaps
- The current `colyseus` core package version and release date were not confirmed from npm/GitHub releases (only the 0.17 changelog and a companion package version).
- Whether WorkAdventure's pusher still uses uWebSockets.js today (vs HyperExpress) and which Phaser version the front uses were not confirmed from current docs.
- No measured bandwidth or latency figures for avatar-position sync were found; the 10 Hz figure above is a design assumption, not a cited number.
